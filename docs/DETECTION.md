# Паттерны детекта деградации и сигналы переключения

Документ фиксирует **что** считается проблемой, **почему** именно так, какие
пороги стоят по умолчанию и как отличить настоящую деградацию от шума.
Реализация: `src/health.rs` (классификация), `src/state.rs` (паттерны,
карантин, выбор). Числа в таблицах — дефолты `Policy`/`ProbeConfig`.

## 1. Откуда берутся сигналы

| Сигнал | Источник | Что видит | Чего не видит |
|---|---|---|---|
| Задержка ноды | `GET /proxies/{tag}/delay?url=…` (sing-box сам дозванивается) | RTT + успех/провал handshake через конкретный аутбаунд | потери пакетов, джиттер |
| Живость ноды | тот же delay | полный отказ, таймаут, отказ TLS | — |
| Блокировка сервиса | delay на **критический** URL (`critical_url`) | 403/406/451 → «выход заблокирован для этого сервиса» | блокировки на уровне DPI внутри TLS |
| Локальный перехват | end-to-end: SOCKS5 → TLS → HTTP через `e2e_proxy` | работает ли inbound/маршрут/селектор целиком | — |
| Состояние селектора | `GET /proxies/{selector}` | `now`, состав `all` | — |
| Ошибки API | те же запросы | Clash API жив, секрет верный, тег существует | — |

Сигналов, которые бы «сами по себе» означали проблему, нет: каждый проходит
классификацию и попадает в счётчик. Ни один единичный таймаут не переключает
трафик.

## 2. Классификация HTTP-ответов

```
accept_status:  [200, 204, 206, 301, 302, 307, 308, 400, 401, 404]
block_status:   [403, 406, 451]
всё остальное (5xx, 429, 418, …) → Inconclusive
```

Почему так:

* **401 — это успех.** `api.openai.com/v1/models` без токена отдаёт 401.
  Значит: TLS прошёл, запрос дошёл, ответ вернулся. Для проверки сетевого пути
  этого достаточно.
* **403/451 — блок, а не смерть.** Нода жива и работает, но конкретный сервис
  её не любит (гео, ASN, WAF). Это отдельный сигнал: не карантин, а
  понижение приоритета.
* **5xx — не вина ноды.** 502/503 от OpenAI, 429 от Cloudflare — это апстрим.
  Считать это отказом ноды значит устраивать ложные переключения во время
  чужих инцидентов. Поэтому `Inconclusive`: ни успех, ни провал, только
  обновление `last_seen` (нода не становится stale).
* **accept проверяется раньше block.** Если оператор внёс 403 в `accept_status`,
  его воля сильнее дефолта (так тестируют ноды с обязательной авторизацией).

Тексты ошибок Clash (`{"message": …}`) классифицируются подстрочным поиском по
lowercase без regex: `timeout|deadline` → `Timeout`, `refused|reset by peer|no
route to host|network is unreachable|eof|tls:|dial tcp` → `Transport`,
остальное → `ApiError` (неизвестная ошибка, тоже провал, но с текстом в логе).

## 3. Паттерны

### P1. Настойчивый отказ — «нода мертва»

**Сигнал:** `consecutive_fails >= fail_threshold` (по умолчанию **2**) жёстких
провалов подряд (`Timeout`/`Transport`/`ApiError`).

**Почему 2, а не 1:** одиночный таймаут — обычное дело (потеря UDP-пакета у
Hysteria2, короткий лаг сети, GC у апстрима). Один провал = подозрение, два
подряд = решение. Это же значение использует EU rollback-guard.

**Действие:** карантин на `quarantine_ms` (300 000 = 5 минут), запись
`quarantine_enter` в audit, если нода активна — немедленное переключение.

**Восстановление:** после истечения окна нужно `recovery_probes` (**2**) успеха
подряд. Карантин sticky: успех до истечения окна не возвращает ноду в пул.

**Чувствительность:** для gaming-профиля `fail_threshold: 1` + `interval_ms:
2000` даёт реакцию ~2–3 s ценой occasional false positive; для массового
трафика дефолт лучше.

### P2. Гео-блокировка — «нода жива, но нас блокирует»

**Сигнал:** `Blocked` (403/406/451) на `critical_url` при живом базовом
эндпоинте. Накапливается в `consecutive_blocks`, ставит `geo_blocked = true`.

**Действие:**
* если есть незаблокированный кандидат — переключиться на него
  (`ActiveBlocked`), даже без ожидания второго блока: сам факт «этот сервис
  здесь не работает» уже достаточен;
* если заблокированы **все** — не переключаться (лучше блокировка, чем мёртвая
  нода) и оставить warning `geo_blocked` в логе;
* `geo_quarantine_ms > 0` (по умолчанию **0**) включает карантин и для блоков —
  имеет смысл, если сервис критичен и нода бесполезна.

**Приоритет протокола:** при наличии блоков включается `protocol_preference`
(по умолчанию `hysteria2 → vless-reality → tuic → vless → anytls → trojan →
shadowsocks → wireguard`), и ранг протокола добавляет
`protocol_rank * protocol_penalty_us` к score. При `protocol_penalty_us: 0`
предпочтение работает только как tie-break. UDP/QUIC и Reality переживают
SNI-блокировки лучше, чем TCP-обёртки — отсюда порядок.

**Проверка гипотезы:** базовый эндпоинт (`1.1.1.1/cdn-cgi/trace`) остаётся
200, а критический даёт 403 — это блок; если оба падают — это P1.

### P3. Деградация задержки — «нода жива, но стала тормозом»

**Сигнал:** EWMA активной ноды превышает `degrade_ms` (**1200 ms**) **или**
`degrade_factor_pct` (**250 %**) от медианы EWMA здоровых нод пула.

**Действие:** событие `degraded` в лог, переключение разрешено **без**
гистерезиса (`margin = 0`), но с соблюдением cooldown.

**Почему два условия:** абсолютный порог ловит «совсем плохо» независимо от
пула; относительный — «эта нода вдвое хуже остальных», что важно, когда весь
пул стало медленнее (тогда переключение не поможет, и относительный порог не
сработает).

### P4. Медленное ухудшение (тренд) — не реализовано сознательно

Идея: отслеживать наклон EWMA за 10–20 семплов и переключаться до того, как
Compound-эффект станет заметен пользователю. Не сделано, потому что:

* на 5-секундном интервале шум сравним с трендом (нужны окна 2–5 минут);
* ложные переключения дороже, чем 10 лишних секунд на медленной ноде;
* реальные деградации в нашей практике — ступеньки (нода умерла/заблокирована),
  которые ловят P1/P2.

Если понадобится: добавить `trend_window` и правило «EWMA растёт 5 семплов
подряд и суммарно +50 % → Degraded». Место — `RouterState::observe`, без
изменения I/O.

### P5. Разрыв локального перехвата — «сломано не там»

**Сигнал:** Clash delay для активной ноды успешен, end-to-end проба через
локальный SOCKS падает (`Timeout`/`Transport`).

**Диагноз:** inbound/маршрут/TPROXY/селектор сломаны на этой машине; нода тут
не виновата. Переключение ноды не поможет и **не выполняется**.

**Действие:** `intercept_probe_failed` (ERROR) + audit `intercept_failure` +
уведомление. Дальше — либо человек, либо внешний rollback-guard
(`eu-watchdog.sh` снимает перехват, чтобы клиенты не сидели без интернета).

**Почему это важно:** без второй пробы «у клиентов не работает» всегда
списывали бы на ноду — и демон бесконечно переключал бы живой пул.

### P6. Флаппинг — гистерезис и cooldown

**Сигнал:** кандидат лучше активной, но незначительно.

**Правила:**
* `switch_margin_pct` (**20**): кандидат должен быть быстрее
  `active_score * (100-20)/100`. 5 ms разницы не повод дёргать TCP-сессии;
* `min_switch_interval_ms` (**1500**): не чаще одного переключения в 1.5 s;
* при мёртвой/заблокированной активной ноды оба ограничения игнорируются —
  это не флаппинг, а спасение;
* tie-break детерминирован `(score, priority, index, tag)` — две ноды с равной
  задержкой не будут переключаться туда-обратно.

**Красный флаг в эксплуатации:** больше 3 переключений за 10 минут на пуле
означает, что пороги не подходят профилю трафика (или что ноды реально
барахлят) — см. audit-рецепты в `ROUTING-AUDIT.md`.

### P7. Массовый отказ — «все умерли»

**Сигнал:** ни одна нода не является кандидатом (все в карантине/stale).

**Действие:** **не переключаться**. Оставить текущую ноду (даже если она
считается мёртвой — вдруг alive), событие `no_healthy_node` (ERROR), запись в
audit, уведомление. Метрика `watchcat_up` остаётся 1: демон работает, пул — нет.

Это важнее, чем кажется: «умное» переключение в этом состоянии лишь меняет
одну дыру на другую и мешает диагностике.

### P8. Мёртвый Clash API

**Сигнал:** `GET /proxies/…` не отвечает/401/404.

**Действие:** никаких изменений состояния и карантинов; backoff 1s → 2s → … →
30s; `clash_api_unavailable` (WARN) с причиной. Если API недоступен, мы не
знаем состав пула и `now` — любые решения были бы гаданием.

### P9. Внешнее вмешательство

**Сигнал:** `now` из API не совпадает с состоянием демона.

**Действие:** при `adopt_external_changes: true` (дефолт) — принять и записать
`active_adopted` с `reason: external_change` (первый синк после старта —
`initial_sync`). При `false` — WARN `selector_drift` и продолжать со своей
моделью (полезно, если селектором управляет кто-то ещё).

### P10. Устаревшие данные

**Сигнал:** `now - last_sample_at > stale_ms` (**60 000**).

**Действие:** нода не кандидат. Защита от «вечно зелёной» ноды, по которой
давно нет проб (например, delay-запросы стабильно падают по причине, которую
классификатор отнёс к Inconclusive).

## 4. Сводная матрица порогов

| Параметр | Дефолт | Смысл | Уменьшить → | Увеличить → |
|---|---|---|---|---|
| `probe.interval_ms` | 5000 | период цикла | быстрее реакция, больше трафика | экономнее |
| `probe.fast_interval_ms` | 1000 | период, пока активная больна | реакция ~1s | меньше пробы при инциденте |
| `probe.timeout_ms` | 2000 | таймаут одной пробы | раньше детект медленных | терпимее к медленным нодам |
| `policy.fail_threshold` | 2 | провалов до карантина | быстрее, больше FP | стабильнее |
| `policy.quarantine_ms` | 300000 | длительность карантина | нода быстрее вернётся | меньше риска «вернуть плохую» |
| `policy.recovery_probes` | 2 | успехов для возврата | быстрее возврат | строже |
| `policy.switch_margin_pct` | 20 | гистерезис | агрессивнее свитчи | стабильнее маршрут |
| `policy.min_switch_interval_ms` | 1500 | cooldown | быстрее серия свитчей | меньше дребезга |
| `policy.degrade_ms` | 1200 | абсолютный порог деградации | чувствительнее | терпимее |
| `policy.degrade_factor_pct` | 250 | относительный порог | чувствительнее | терпимее |
| `policy.stale_ms` | 60000 | протухание семпла | строже | лояльнее |
| `probe.critical_every_ticks` | 3 | частота проверки блокировок | чаще ловим блок | меньше запросов |

**Реакция по времени (дефолт 5 s / 2 провала):**

* активная нода умерла сразу после тика → первый провал на +5 s, второй на
  +6 s (включился fast-mode 1 s) → переключение на +6 s;
* умерла за миг до тика → переключение на +1–2 s;
* худший случай — около `interval_ms + fast_interval_ms ≈ 6 s`;
* само переключение (PUT по loopback) — **< 1 ms**, sing-box не перезапускается,
  существующие TCP-сессии идут по старому маршруту до закрытия, новые — по
  новому.

## 5. Ложные срабатывания: таблица разбора

| Симптом в логе | Вероятная причина | Что делать |
|---|---|---|
| `quarantine_enter` у всех нод одновременно | локальная сеть/шлюз/Clash API, а не ноды | проверить `ip route`, `curl` к API, DNS; при API-ошибке демон не должен был это делать |
| `geo_blocked` у всех нод | критический URL недоступен из страны в принципе (или 451 у всех) | сменить `critical_url`/сервис, `geo_quarantine_ms: 0` |
| `degraded` на всех нодах | весь пул стал медленнее (пик нагрузки на апстрим) | ничего: относительный порог не даст переключаться |
| частые `route_switch` туда-обратно | маргин слишком мал или ноды с равной задержкой | поднять `switch_margin_pct` до 30–40 |
| `intercept_probe_failed` при живом delay | TPROXY/redirect/inbound на машине | `journalctl -u sing-box`, `ip rule`, `ip route show table 100` — см. `env/dev/servers/ROUTING.md` §2.1 |
| `no_healthy_node` | все в карантине/все stale | смотреть `fails_total` и `last_seen` в метриках; проверить, что `all` в селекторе не пуст |
| `clash_api_unavailable` | sing-box упал / сменили секрет / не тот порт | `systemctl status sing-box`, сверить `secret` |
| `configured_node_not_in_selector` | конфиг ссылается на тег, которого нет в `selector.outbounds` | поправить конфиг или config.json sing-box |

## 6. Что сигналом **не** является

| Наблюдение | Почему нет |
|---|---|
| нет клиентского трафика через ноду | нода может просто не быть выбранной; отсутствие трафика ≠ отказ (это же правило записано в EU rollback-guard) |
| нет ответа на ICMP | ICMP режут массово, а UDP-протоколы (WG/H2) на него не отвечают by design |
| UDP молчит | Hysteria2/WireGuard не отвечают на мусор; нужен валидный handshake, его и делает delay-проба |
| 5xx от OpenAI | апстрим, а не нода (см. §2) |
| одна медленная проба | шум; EWMA и порог из двух провалов это гасят |

## 7. Чем это отличается от `urltest`

`urltest` проверяет «какой из нод ответил быстрее» и переключается по
`tolerance`. Он не различает «мертва» и «заблокирована», не умеет карантин с
восстановлением, не видит локальный перехват и не пишет причину переключения.
watchcat добавляет именно эти четыре вещи — и поэтому пороги имеют смысл:
каждое число в §4 привязано к конкретному сигналу, а не к «на глазок».
