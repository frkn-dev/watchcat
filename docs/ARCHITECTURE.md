# Архитектура watchcat

Демон-наблюдатель за выходными нодами sing-box. Управляет **только** выбором
аутбаунда в селекторе через Clash API: без перезапуска sing-box, без правки
iptables, без участия в жизни клиентских пиров.

## 1. Место в схеме

```
клиент (AWG/WG)
  → [REDIRECT/TPROXY]  sing-box: inbound → route.rules → selector main-outbound
                                                            ↑
                                            PUT /proxies/main-outbound
                                                            │
                                          watchcat ─ GET /proxies/main-outbound
                                                   └─ GET /proxies/{tag}/delay
                                                   └─ (опц.) SOCKS5 → TLS → GET https://…
  → выбранная нода (vless-reality / hysteria2 / tuic / ss / wg)
```

watchcat живёт рядом с sing-box на той же машине и общается с ним по loopback.
Никаких данных через него не проходит: это управляющий контур, а не дата-план.

### Почему не встроенный `urltest`

`urltest` в sing-box умеет «выбери самый быстрый из списка» и этого мало:

| Требование | `urltest` | watchcat |
|---|---|---|
| Проверка живости по URL | да | да (Clash delay + e2e) |
| Отдельный сигнал «нода жива, но нас блокирует» | нет | да (403/451 на критическом эндпоинте) |
| Карантин с восстановлением по N успехам | нет | да |
| Гистерезис и cooldown против флаппинга | только `tolerance` | да (`switch_margin_pct`, `min_switch_interval_ms`) |
| Приоритет протокола при блокировках | нет | да (`protocol_preference`) |
| Проверка локального перехвата (inbound жив?) | нет | да (end-to-end проба через SOCKS) |
| Журнал «кто, когда, почему переключил» | нет | да (audit JSONL) |
| Ручное переключение без рестарта | нет | да (`--set`, UI, curl) |

`urltest` по-прежнему уместен там, где нет Clash API (например, relay-a сейчас).
Перевод на `selector + watchcat` описан в `OPERATIONS.md` §4.

## 3. Один тик

`Supervisor::tick()` — линейная последовательность, каждый шаг которой может
«ничего не делать», но не может оставить систему в полу-состоянии:

1. **`GET /proxies/{selector}`** — `now` (текущая нода) и `all` (состав пула).
   Ошибка здесь ≠ отказ ноды: состояние не мутируется, логируется
   `clash_api_unavailable`, backoff удваивается (1s → 30s).
2. **Сверка пула.** Конфиг задаёт список — он главнее; пусто — берём `all` из
   API. Порядок из API сохраняется: это база для детерминированного tie-break.
3. **Принятие внешнего переключения.** Если `now` в API разошёлся с нашим
   состоянием (оператор дёрнул селектор руками), демон принимает это как истину
   и пишет `active_adopted` в audit. Воевать с оператором — плохая идея.
4. **Пробы.** `GET /proxies/{tag}/delay?url=…` для всех нод пула, пачками по
   `probe.concurrency`; критический эндпоинт — раз в `critical_every_ticks`.
5. **Свёртка** base+critical в один исход на ноду (живость — из base, блок — из
   critical) → `observe()` в машину состояний.
6. **end-to-end проба активной ноды** через локальный SOCKS (если `method !=
   clash_delay`). Даёт две вещи: подтверждение, что путь клиента работает, и
   диагностику «умер не там».
7. **`decide()`** → при необходимости `PUT /proxies/{selector}` c
   `{"name":"…"}`, запись в audit, уведомление.
8. **Метрики** (атомарная перезапись textfile) и итоговая строка `tick`.

Замер на 10 нодах, оба типа проб, интервал 1s: длительность тика 2 ms,
`probe`-запросы к loopback 0.2–0.5 ms каждый.

## 4. Модель состояния

```
Outcome            что значит                              счётчики
─────────────────────────────────────────────────────────────────────────────
Ok                 ответ 200/204/401 и т.п.                 fails=0, ok++, EWMA
Blocked            403/406/451 на критическом URL           blocks++, geo_blocked
Inconclusive       5xx/429 — виноват не узел                ничего (только last_seen)
Timeout            нет ответа за probe.timeout_ms           fails++, total++
Transport          refused/reset/TLS/мусор                  fails++, total++
ApiError           Clash API вернул ошибку по аутбаунду     fails++, total++
```

* `consecutive_fails >= fail_threshold` → карантин на `quarantine_ms`.
* Карантин **sticky**: сам по себе по времени не снимается, нужен
  `recovery_probes` успехов подряд после истечения окна. Иначе нода вернётся в
  пул на первом же случайном успехе.
* `geo_blocked` не отправляет ноду в карантин (по умолчанию
  `geo_quarantine_ms: 0`): она годна для обычного трафика, просто хуже для
  конкретного сервиса.
* EWMA целочисленный: `ewma = (ewma*(1000-α) + sample*α)/1000`, α=300‰.
  Никаких float — одинаковый результат на любой платформе и при любом прогоне.

## 5. Как выбирается кандидат

```
candidates = ноды, у которых:
    есть свежий семпл (now - last_sample_at <= stale_ms)
    нет карантина
    (при наличии заблокированных — не заблокирована)

score = ewma_us + protocol_rank * protocol_penalty_us
порядок: (score, priority, index, tag) — стабильный, без рандома
```

Дальше три сценария (`decide`):

| Ситуация | Действие |
|---|---|
| активной нет / её выкинули из пула | переключиться на лучшего (`NoActive`/`ActiveMissing`) |
| активная в карантине или заблокирована | переключиться **сразу**, игнорируя cooldown и margin (`ActiveFailed`/`ActiveBlocked`) |
| активная здорова | переключаться только если кандидат быстрее на `switch_margin_pct`, и не чаще `min_switch_interval_ms` (`BetterCandidate`/`ActiveDegraded`) |
| кандидатов нет | **не переключаться**: оставить текущую ноду и закричать `no_healthy_node` |

Принцип: лучше оставить трафик на живой (пусть и медленной) ноде, чем увести
всех в мёртвую или в никуда.

## 6. Детерминизм

Проверяемые свойства (есть тесты):

* монотонные часы: все окна/карантины считаются в `mono_ms`, NTP-скачок не
  влияет; wall clock — только для записи `ts` в лог;
* целочисленный EWMA;
* стабильная сортировка кандидатов с явным tie-break;
* никаких случайных задержек и «джиттера» в алгоритме;
* машина состояний не делает I/O — только чистые переходы, поэтому сценарий
  «2 таймаута → карантин → переключение» воспроизводится в тесте с точностью
  до миллисекунды.

## 7. Производительность

Измерено на macOS arm64 (release, LTO, strip):

| Метрика | Значение |
|---|---|
| размер бинаря | **1.7 MB** (`mock-clash` — 475 KB) |
| RSS при 10 нодах, 1s интервал, оба типа проб | **2.5–3.5 MiB** |
| CPU | 0.1–0.7 % одного ядра |
| длительность тика (10 delay + 1 e2e) | **2 ms** |
| переключение: `PUT` по loopback | < 1 ms |
| запросов в сеть за тик | 10 delay (+5 critical раз в `critical_every_ticks`) + 1 e2e |

Решения, которые это дают:

* **`current_thread` runtime.** Работа — ожидание сети, а не счёт. Один поток
  убирает пул воркеров, лишние стеки и переключения контекста.
* **Свой HTTP/1.1 клиент.** Нам нужны три запроса к loopback и один POST в
  Telegram; hyper/reqwest притащили бы десятки крейтов и мегабайты кода.
* **Нет пула соединений.** `connect()` на loopback — десятки микросекунд, пробы
  идут параллельно, а переиспользование сокета требует таскать частично
  прочитанные буферы между запросами. Риск не оправдан при 2–10 req/s.
* **Пробы через Clash API.** sing-box сам дозванивается до ноды: наши процессы
  не открывают сокеты на каждую ноду и не дублируют TLS-стек ядра.
* **Ограниченный параллелизм** (`probe.concurrency`) — не «лавина» из 100
  одновременных проб.
* **Буферы переиспользуются** (`Vec` в логгере и метриках), тела ответов
  ограничены 4 MiB, чтобы битая нода не съела память.
* **Без regexp:** все парсеры на nom, компилируются в обычный код, ничего не
  интерпретируется в рантайме.

Целевой профиль на сервере: RSS < 10 MiB, CPU < 1 % при пуле 10 нод и
интервале 5s.

## 8. Самокоррекция и отказоустойчивость

| Отказ | Поведение |
|---|---|
| Clash API недоступен | состояние не меняется, backoff до 30s, метрика `api_errors_total` |
| `PUT` отклонён (400/500/timeout) | ошибка в лог, `switch_failures_total`, audit с `api_ok:false`; на следующем тике состояние сверяется с API (`active_adopted`) — расхождение исчезает само |
| селектор переименовали/удалили | `selector_missing`, демон не падает и продолжает пытаться |
| audit-файл не пишется | один ERROR, журнал отключается, **роутинг продолжает работать** |
| Telegram недоступен | сообщение теряется, счётчик, цикл не блокируется (канал ограничен) |
| проба упала паникой | пропущенный семпл, нода помечается stale, пул живёт |
| SIGTERM/SIGINT | graceful shutdown, `shutdown` в лог, audit уже сброшен на диск |

## 9. Границы ответственности

watchcat **не** делает:

* не поднимает/не перезапускает sing-box и интерфейсы — это systemd и
  `awg-quick`;
* не правит iptables/TPROXY (см. `env/dev/servers/ROUTING.md`);
* не добавляет и не удаляет ноды в конфиге sing-box — только выбирает из того,
  что уже есть в селекторе;
* не балансирует клиентов между нодами (это делает API/`fnode` через пулы);
* не заменяет rollback-guard перехвата (`eu-watchdog.sh`) — он про другое:
  «если sing-box умер, снять перехват». См. `DETECTION.md` P5.
